# WireGuard VPN — the only way into the platform (OKD node)

**Principle:** the platform is reached through the VPN only, from the local network as well as from outside; the local network is **never** reachable from the VPN. Service names point to the server's VPN address (see `../../ingress/`). The VPN is therefore also the **only administration path**: nothing below may cut it.

## Variables

No value from the reference installation is given here: pick your own.

| Variable | Role | Shape |
|---|---|---|
| `${VPN_NETWORK}` | VPN network, a private /24 overlapping neither the local network nor the pod and Service networks | `a.b.c.0/24` |
| `${VPN_SERVER_IP}` | server address on the VPN, also Forgejo's externalIP and the target of DNS names | `a.b.c.1` |
| `${VPN_ADMIN_RANGE}` | range of administration devices: whole node, Forgejo SSH and web | `a.b.c.x-a.b.c.y` |
| `${VPN_PREFIX}`, `${VPN_HOST_MIN}`, `${VPN_HOST_MAX}` | `add-peer.sh` checks: `a.b.c` prefix and assignable last octet | — |
| `${VPN_PORT}` | UDP listening port, forwarded by the upstream router or firewall | — |
| `${LAN_NETWORK}` | the node's local network, never routed into the VPN | — |
| `${GIT_SSH_PORT}`, `${GIT_HTTP_PORT}` | Forgejo ports exposed on the externalIP | — |
| `${JVB_UDP_PORT}` | UDP port of video call media, exposed on the same externalIP (section 6) | — |
| `${DEV_GATEWAY_VPN_PORT}` | SSH port of the dev gateway on the same externalIP, reserved to administration (section 7) | — |
| `${LAN_NODE_IP}` | the node's address on the local network: out-of-VPN administration fallback (section 7) | — |

Any address outside `${VPN_ADMIN_RANGE}` is a **user** device: HTTP/HTTPS only.

## Files

| File | Role |
|---|---|
| `wg-filter.nft` | template of the `inet sophia_wg` nftables table, independent from OVN-Kubernetes: **administration** → whole node + Forgejo; **users** → 80/443 only; **nothing is forwarded** to the local network, pods or Services, except Forgejo for administration (and the rules added in sections 6 and 7) |
| `sophia-wg-filter.service` | loads the filter at boot, before the network, then runs the safeguard |
| `wg-filter-check.sh` | **safeguard**: re-reads the whole ruleset with OVN-Kubernetes' nft; unreadable → deletes the table and raises a journal alert (the cluster comes first, the VPN is **never** cut) |
| `test-garde-fou-metrique.sh` | local bench, **Linux only**: compares the old and new safeguard with fake `crictl`, `podman`, `nft` and `logger` |
| `sophia-wg-filter-check.{service,timer}` | re-runs the safeguard 3 min after boot, then every 15 min (OKD updates) |
| `test-nft-ovn.sh` | tests, expression by expression, what OVN's nft can read back (hook-less tables, deleted immediately) |
| `add-peer.sh` | adds a device: name, address, **public key**; checks (format, duplicates, range), profile backup, applied without dropping tunnels; if applying fails, stops (code 2) with the peer written in the profile, **never restarting `wg0`** |

## 1. Server-side interface

`wg0` is a **kernel** interface managed by **NetworkManager** (profile `/etc/NetworkManager/system-connections/wg0.nmconnection`, mode 600); no extra package is needed on the node.

| Item | Value |
|---|---|
| Address | `${VPN_SERVER_IP}/24` |
| Port | UDP `${VPN_PORT}`, forwarded from the public address (router, firewall) |
| Private key | generated **on the node**, never copied elsewhere; only the public key is given to devices |
| Peers | one per device, `allowed-ips` = its /32 address |
| OKD FORWARD | **DROP** policy: only pod and Service networks are forwarded, the local network is already unreachable |
| Forgejo | externalIP `${VPN_SERVER_IP}` on `${GIT_SSH_PORT}` and `${GIT_HTTP_PORT}`, DNAT to its Service |

Without the filter, **every peer reaches every port of the node** (SSH, cluster API, kubelet, etcd, machine config server, agents API…), and pods and Services directly if it widens its `AllowedIPs`: hence section 3.

**At home**, the tunnel goes through the public address (`Endpoint`): the router must loop the traffic back inside (*hairpin NAT*). Check it with the first device on Wi-Fi.

## 2. Adding a device

1. On the device, **WireGuard** app → *Add a tunnel* → *Create from scratch*: the app **generates the key**; note the displayed **public key** (never the private one).
2. On the node:
   ```bash
   sudo VPN_PREFIX=<a.b.c> VPN_HOST_MIN=<min> VPN_HOST_MAX=<max> \
     ./add-peer.sh <device-name> <VPN address> '<public key>'
   ```
3. On the device, complete the tunnel:
   ```ini
   [Interface]
   PrivateKey = (generated by the app)
   Address = <VPN address>/32
   [Peer]
   PublicKey = <server public key>
   Endpoint = <public address>:${VPN_PORT}
   AllowedIPs = ${VPN_NETWORK}
   PersistentKeepalive = 25
   ```
   No `DNS =`: public DNS already answers `${VPN_SERVER_IP}`. `AllowedIPs` limited to the VPN network: the device's local network is not diverted.
4. iOS: *On-Demand Activation* on Wi-Fi **and** cellular. Android: *Settings → Network → VPN → ⚙ → Always-on VPN*.

Record each device in the peer comment (done by `add-peer.sh`); keep administration addresses for administration workstations only.

### iOS devices: video calls and the default network

On an iPhone or iPad, the profile adds **`8.8.8.8/32`**:

```ini
AllowedIPs = ${VPN_NETWORK}, 8.8.8.8/32
```

**Why**: WebKit's WebRTC on iOS (Safari, and Chrome, which uses the same engine) only enumerates the "default" network interface, and libwebrtc determines it by opening a UDP socket towards `8.8.8.8`, without sending anything. With the base profile, that interface is the Wi-Fi or mobile network: the device only offers that address as a candidate, and the video media never goes through the tunnel, while its pages do. With the route to `8.8.8.8` in the tunnel, the VPN becomes the "default" interface for WebRTC; the rest of the Internet stays outside the tunnel. Real case: without this setting, the call opened on the tablet, but picture and sound never reached the bridge ([Communication module](../../../../docs/modules/communication/documentation.en.md#video-media-three-causes-in-a-row)).

- **Side effect**: an application that queries `8.8.8.8` directly as its DNS server goes through the tunnel, where the filter refuses it; the system DNS is not affected.
- **IPv6**: no equivalent needed as long as the bridge only advertises an IPv4 address and the tunnel has no IPv6.
- **Android**: base profile. Chrome on Android enumerates every interface, VPN included, once camera or microphone are allowed (to be confirmed by testing each device); `8.8.8.8/32` is only added if it requires it: with Android's private DNS set to that provider, all of the phone's DNS would be refused.
- **Test each device**, at home then on the mobile network: a diagnostic page served by the video service lists the device's ICE candidates (camera allowed long enough to unmask them); a `host` candidate within `${VPN_NETWORK}` is expected. The page is removed once every device has been tested.

## 3. Filter (administrator, on the node)

From an **administration** workstation (the session stays open whatever happens).

```bash
# render the template (EXPLICIT list: the nft code's "$" are left alone)
export VPN_SERVER_IP=… VPN_ADMIN_RANGE=… GIT_SSH_PORT=… GIT_HTTP_PORT=…
envsubst '$VPN_SERVER_IP $VPN_ADMIN_RANGE $GIT_SSH_PORT $GIT_HTTP_PORT' < wg-filter.nft > wg-filter.rendu.nft
grep -n '\${' wg-filter.rendu.nft && echo "⚠ unrendered variable" || echo "fully rendered"
# copy to the node: wg-filter.rendu.nft, wg-filter-check.sh, test-nft-ovn.sh, the three systemd units
# on the node
sudo nft list ruleset > ~/backup-nft-$(date +%Y%m%d).txt          # backup
sudo bash test-nft-ovn.sh                                          # compatibility with OVN's nft
sudo mkdir -p /etc/sophia
sudo install -m 644 wg-filter.rendu.nft /etc/sophia/wg-filter.nft && sudo install -m 755 wg-filter-check.sh /etc/sophia/
sudo nft -c -f /etc/sophia/wg-filter.nft && echo "syntax OK"          # check only, applies nothing
# dead-man switch: the table is dropped in 3 min unless cancelled (the tunnel is untouched)
sudo systemd-run --unit=wg-filter-deadman --on-active=180 /usr/sbin/nft delete table inet sophia_wg
sudo nft -f /etc/sophia/wg-filter.nft && sudo /etc/sophia/wg-filter-check.sh; echo "safeguard=$?"   # must be 0
# → from the administration workstation: NEW SSH session, git fetch, web interface; then:
sudo systemctl stop wg-filter-deadman.timer
sudo install -m 644 sophia-wg-filter.service sophia-wg-filter-check.service sophia-wg-filter-check.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable sophia-wg-filter sophia-wg-filter-check.timer
sudo systemctl restart sophia-wg-filter && sudo systemctl start sophia-wg-filter-check.timer
systemctl is-active sophia-wg-filter; journalctl -t sophia-wg-filter -n 5
```

**Check:**
- administration workstation: SSH, `git fetch` on `${GIT_SSH_PORT}`, web interface;
- user device: the interface answers; a server port other than 80/443 (the agents API, for instance) **does not answer** (the page loads forever), and the counter goes up:
  ```bash
  sudo nft list chain inet sophia_wg input | grep counter
  ```

**Rollback:** `sudo nft delete table inet sophia_wg` (immediate); `sudo systemctl disable --now sophia-wg-filter` (permanent).

Avoid any iptables `FORWARD` rule accepting a forwarded port "for `wg0`": it opens that port to **all** peers as soon as the table is missing. The externalIP DNAT to the Service network is already accepted by OKD.

## 4. Compatibility with OVN-Kubernetes

**Incident (OKD 4.21):** after a power cut, no pod had a network any more (`ovnkube-node` in CrashLoopBackOff, multus timing out), hence no Forgejo, hence nothing depending on it. `ovnkube-controller` re-reads the **whole ruleset** at start with its image's nft (**1.0.9**, versus 1.1.5 on the host) and segfaulted (code 139) on the `inet sophia_wg` table. Before the power cut everything worked because the table had been loaded **after** OVN started: the defect only shows on restart.

**Cause isolated** with `test-nft-ovn.sh` (one test table per expression, **without base chain**, hence no effect on traffic, deleted immediately): **any named set** (`set admins { … }`, `@admins`), with or without intervals, in the `inet` and `ip` families alike. The expression first suspected (`ct original ip daddr`) is readable. Fix: administration range written inline in the rules, same security intent.

**Safeguard:** `wg-filter-check.sh` re-reads the whole ruleset with OVN's nft — `crictl exec` in the `ovn-controller` container when it runs, otherwise `podman` with the last image seen (at node boot CRI-O is not there yet). Codes: 0 readable; 1 unreadable → **table deleted**, `crit` journal alert, unit failed; 2 check impossible → table kept, warning. The choice is deliberate: when in doubt, **the cluster and administrative access come first**, the VPN stays open without filter until fixed; cutting the VPN would deprive the administrator of the only way in.

**After every OKD update** (the nft in the OVN image may change):

```bash
sudo /etc/sophia/wg-filter-check.sh; echo $?          # 0 expected; 2 = OVN unreachable
systemctl status sophia-wg-filter sophia-wg-filter-check.timer
journalctl -t sophia-wg-filter -n 20                  # "ALERTE … SUPPRIMÉE" = filter removed
sudo bash test-nft-ovn.sh                             # on alert: which expressions break
```

If the safeguard removed the table: the cluster runs but **the VPN is no longer filtered** — fix `wg-filter.nft` according to `test-nft-ovn.sh`, then go through section 3 again.

**Rules to keep:** never run `nft flush ruleset`; never touch OVN or OpenShift tables; every nftables test happens in a **hook-less** table deleted right away; every filter load happens under a dead-man switch.

## 5. Safeguard as a metric

On each run, the safeguard writes its code (0 readable, 1 table removed, 2 check impossible) and a timestamp to `/var/lib/sophia/metrics/wg_filter.prom`, read by the node exporter ([`../../monitoring/`](../../monitoring/)). Three alerts follow: filter removed, check impossible, safeguard silent for more than 45 minutes. The write is atomic (temporary file, then `mv`) and **every error is ignored**: the safeguard's decisions, actions and exit codes do not change.

This is the only administration path: a change to the safeguard is installed with the same care as the filter.

1. **Bench, before any installation**: `bash deploy/okd/host/wireguard/test-garde-fou-metrique.sh <copy of the old script>`, at the repository root, on Linux. It crosses 5 OVN-Kubernetes scenarios with 3 states of the metric file (writable, missing, in error); the exit code and the exact sequence of actions must be identical. Expected: `AUCUN ÉCART (15 cas)`; otherwise, do not install. The bench refuses to run without GNU `sed` (code 2): the safeguard uses `\+` in its expressions, which BSD `sed` does not understand, and a bench run elsewhere would not prove the node's behavior.
2. **Installation**, outside usage hours, with the administration session kept open: `bash -n`, old script set aside on the node, installation, then **one run identical to the timer's**, without reloading the filter or restarting `sophia-wg-filter.service`. Expected: `garde-fou=0`, `sophia_wg_filter_code 0` and a timestamp in the file, table present; on the timer's next run, the timestamp moves forward.
3. **Rollback in one command**: reinstall the old script set aside and run it once.

## 6. Video call media

The video service of the [Communication module](../../../../docs/modules/communication/documentation.en.md) (installed, in acceptance testing) carries its media over **a single UDP port**, exposed like Forgejo through an externalIP on `${VPN_SERVER_IP}`, not through a NodePort: a NodePort would be reachable from the local network, and the bridge would only see OVN-Kubernetes' join address there. The service's recipe is in [`../../office/`](../../office/README.en.md#persistent-chat-and-video-calls).

A rule, open to **every** VPN device (users included), to place before the `counter drop` of `forward`:

```
ct original ip daddr ${VPN_SERVER_IP} udp dport ${JVB_UDP_PORT} counter accept comment "video: media"
```

Add `$JVB_UDP_PORT` to `envsubst`'s explicit list, then load the filter as in section 3: `nft -c` check, **3-minute automatic switch**, which reloads the previous filter (or removes the table), safeguard at 0, new administration session, then stop the switch. The bridge's replies to devices go through `ct state established,related`.

**This rule's counter is not a check**: it stayed at zero during a call whose media was established. The path has since been measured (section 7.1): redirected traffic does go through the `forward` chain and the rule counts its packets, but a zero counter does not prove there is no media, and a rising counter does not prove media flows. What counts as proof:

- the media bridge's debug state (participants `iceConnected`, packets received and sent);
- the node's connection-tracking table (`/proc/net/nf_conntrack`): one entry per device towards `${VPN_SERVER_IP}:${JVB_UDP_PORT}`, without `[UNREPLIED]`.

On the cluster side, the bridge pod sees a source rewritten by the host masquerade: its NetworkPolicy admits the `host-network` group on that port (see the [recipe](../../office/README.en.md#persistent-chat-and-video-calls)). iOS devices need their own profile (section 2).

## 7. Exposure outside the VPN: what the filter review measured and fixed

A review of the filter asked two questions: can a VPN device reach, through an externalIP, a service the filter denies it? And is any service reachable without going through the VPN? Read-only measurements on the node (`nft list ruleset`, `ip route get`, `ovs-ofctl dump-flows br-ex`, filter counters), then two changes.

### 7.1 Measured: the filter sees redirected traffic, with the Service port

With OVN-Kubernetes' shared gateway, an externalIP's DNAT is done **by the kernel, in prerouting** (table `ip nat`, chain `OVN-KUBE-EXTERNALIP`), hence **before routing**. The translated packet is then routed towards `br-ex`: it is forwarded, and goes through the `forward` chain of `inet sophia_wg`. During a video call, the media rule counts its packets, and the "nothing forwarded" drops rise for whatever is not admitted.

Consequences:

- **no bypass through the VPN**: a user device reaches neither Forgejo nor any other service published on `${VPN_SERVER_IP}` outside a rule; a filter placed in prerouting is not needed;
- **the port seen by `forward` is the Service port after DNAT**, neither the device's nor the pod's: a rule is written on the Service port (`port`), which must differ for each Service published on the same address.

### 7.2 Pitfall fixed: a NodePort is served on the local network

A NodePort is translated for **every local address of the node** (`fib daddr type local`), hence also for its local-network address. The filter's `forward` chain only looks at what comes in through `wg0`: a NodePort escapes "access through the VPN only". This was the case of the development SSH gateway.

Fix: the NodePort is replaced by **a Service with an externalIP on `${VPN_SERVER_IP}`**, like Forgejo and the video calls ([`../../pod-bases/dev-bastion/dev-gateway-service.yaml`](../../pod-bases/dev-bastion/dev-gateway-service.yaml)):

- two Services: `dev-gateway`, ClusterIP only, and `dev-gateway-vpn`, which carries the externalIP. An externalIP applies to **all** ports of a Service, and the pod's SSH port may already be taken on `${VPN_SERVER_IP}` by Forgejo: two translations for the same address and port, one would win at random;
- the port of `dev-gateway-vpn` is **reserved to the administration range** by one more rule, before the `counter drop` of `forward`:

```
ip saddr ${VPN_ADMIN_RANGE} ct original ip daddr ${VPN_SERVER_IP} tcp dport ${DEV_GATEWAY_VPN_PORT} counter accept comment "administration: dev gateway"
```

Order: the filter first (its rule is moot until the Service exists), loaded as in section 3, under the automatic switch; then the Services (`oc diff`, `apply --dry-run=server`, apply). Checks: SSH to the gateway through the VPN from an administration device, and the rule's counter rising (here it does prove the path); from the local network, `nc -vz ${LAN_NODE_IP} <former NodePort>` answers `Connection refused`.

**Inventory to run on any installation**: `oc get svc -A --field-selector spec.type=NodePort` and `LoadBalancer` Services. Each one is served on the local network.

### 7.3 externalIP admission limited to the VPN address

By default (`network.config` `cluster`, `spec.externalIP.policy: {}`), **any address** is admitted as an externalIP: an account that is admin of its own namespace only could publish a Service on a local-network address. Admission is limited to the VPN address:

```bash
oc patch network.config cluster --type=merge -p '{"spec":{"externalIP":{"policy":{"allowedCIDRs":["${VPN_SERVER_IP}/32"]}}}}' --dry-run=server -o jsonpath='{.spec.externalIP}'
```

then the same patch without `--dry-run`. Rollback: `allowedCIDRs: null`, never `policy: null` (which would deny every externalIP, Forgejo included).

Two caveats:

- **a `cluster-admin` account is not subject to this admission**. A test under your own admin account, with a test Service on a local-network address, is therefore admitted and proves nothing. The test runs under a limited account, with `--dry-run=server`: `oc apply --dry-run=server --as=system:serviceaccount:<namespace>:<admin account of that namespace> -f <test service>`, expecting `Forbidden`; existing Services (Forgejo, video, gateway) stay admitted. What remains outside the restriction: accounts bound to `cluster-admin`, to be kept few;
- the change produces **a new kube-apiserver revision**. On a single node, the API stops answering for a few minutes: `oc` fails, and so does every tool depending on it (agents, consoles). Pods, the VPN, SSH, Forgejo and video calls keep running. Before this change: warn that control will be lost, give the rollback and the section 7.4 fallback in advance, and pick a quiet moment.

### 7.4 Administration fallback over the local network, outside the VPN

The VPN is the only administration path. If it goes down, `${VPN_SERVER_IP}` (the `wg0` address) may vanish: targeting it from the local network is useless. The fallback targets **the node directly**, on `${LAN_NODE_IP}`, over key-based SSH: the node's sshd listens on every address, and the `inet sophia_wg` table only filters `wg0`. From the node, one hops to the dev gateway's ClusterIP or to any internal service.

It is a deliberate, narrow exception: the home local network, key-based SSH, to the node only. It is tested **before** any change to the filter, the Services or the API (VPN off on the test device, connection to the node, hop to the gateway), and is never removed without another fallback in place.

## Open points

- Cleaner later: ship these files through a `MachineConfig`, like the rest of the node configuration. On a single node, applying a MachineConfig **reboots the node**: to be planned.
- The dev gateway's NetworkPolicy admits its SSH port from the whole cluster: to be tightened.
- OVS can also deliver `${VPN_SERVER_IP}` arriving on the local-network card, if a machine on that network routes this address to the node. Low exposure, untested, counters at zero.
- The safeguard alerts in the node journal and as a metric (section 5); its `warning` and `critical` alerts go to the administrator outside the platform, through the Alertmanager's general route ([`../../monitoring/`](../../monitoring/)); the "incident" workflow remains planned.
